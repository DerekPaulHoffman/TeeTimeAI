# Own failed learning through customer recovery

This contract applies when the server-persisted action plan includes `INVESTIGATE_PUBLIC_SOURCE` alongside `IMPLEMENT_REUSABLE_SUPPORT`. It supersedes stage-only research and stop instructions for that assignment. The dispatcher validates an actual terminal learner job, unchanged source and current alert generation before granting it. Checkpoints cannot grant permission. Legacy verify-only assignments keep their original authority.

The mission is the customer's result: understand the public inventory, repair the reusable process, independently execute the saved method, persist matching times, and observe normal application delivery. A successful command or release is intermediate evidence.

## Investigate like the interactive owner

1. Read the owned packet, `research-context`, original failure diagnosis, prior attempts and provider notes. Keep a compact private record of the failing boundary, evidence, hypothesis, different next approach, and observation that would disprove it. Never copy identities, URLs, bodies or credentials into aggregate notes. Preserve the failed job and original clock.
2. Use Sol through ChatGPT sign-in. Discover browser inventory with supported CUA tools and select **First user** by profile metadata; never select the work profile or guess a transient browser ID. Inspect course inventory signed out; do not use personal course accounts. Missing native browser capability is a tooling fault, not an inaccessible venue.
3. Follow official navigation and embedded frames. Inspect rendered identity, address/phone, calendars, standard Public inventory and public date/player controls. If the root lacks booking navigation, use bounded exact venue/locality web research and corroborate the provider against official identity. Search snippets alone cannot establish a method. Failed HTTP is not proof the rendered page is unreadable. Failed extraction is not proof a person cannot find inventory. This action permits native read-only browser/web research; it does not broaden the separate `source-search-context` or static inspector command gates.
4. Compare observed public behavior with the failed execution. Distinguish identity, navigation/frame, transport, completeness, parameter binding, replay, persistence, scheduler and delivery failures. A missing complete contract cannot prevent fixing the discovery tool: `validate-research-context` reports `discoveryToolingRepairMayProceed` separately from permission to implement a proven provider contract. Neither activates data or supplies monitoring proof.

   The explicit `TOOLING_ONLY_NO_ACCESS_OVERRIDE` scope may remain available while historical HTTP/restricted-network or authentication/challenge evidence is retained as `BARRIER`. It authorizes diagnosis and repair of owned discovery/runtime code, never a new provider read, access override, source/configuration write or recipe activation. Follow the current action plan for public research; an actual denied access or challenge still stops that access operation. Preserve the barrier until fresh appropriately authorized evidence reconciles it. `furtherBoundedInspectionRequired` describes missing provider proof and is not a stop on explicitly permitted tooling repair. Claim paths first, fix the concrete reproducible tooling failure and require tested deployment and independent replay.
5. Claim paths and exclusive implementation authority before edits. Fix reusable behavior and add a regression from the real failure shape. Do not hardcode this venue's source or identity instead of learning it. Preserve provider request limits, installed Local Reader identity/settings/permissions, public URL/DNS checks, ownership, cancellation and replay. If another implementation owner holds the lock, retain this mission and wait boundedly with its lease; do not edit around it.

## Carry the repair across boundaries

First use the owned current-runtime discovery/verification when existing support can learn the required configuration. A data-only repair requires independently verified saved configuration and normal monitoring, not a dummy code change. A negative result retains this same owner. If actual reader/runtime code is missing or faulty, claim its paths, fix the real defect and run focused tests, required exact-head CI, the exact committed release heartbeat, Git publication and owner-bound `verify-release`. Once any code path is claimed, unchanged-runtime verification cannot satisfy implementation proof. Every distinct candidate needs its own registered SHA and verification. Never replay an ambiguous mutation or rejected heartbeat. Follow-up releases must descend from the persisted release and retain previous evidence.

An optional-code full mission with zero claimed paths and no changed release is not an unfinished code implementation merely because its primary action is IMPLEMENT_REUSABLE_SUPPORT. Expired recovery keeps the ordinary source, execution, ownership and retry-budget checks and can safely requeue that unresolved data-only mission. Code-bearing missions retain the strict implementation-proof requirement. The normal engineering handoff reconciler corrects only the exact prior `expired_implementation_stopped_without_proof` data-only misclassification: current active demand, same source, no active owner or newer successful monitoring, and one completed matching full mission. It preserves the failed batch, result, incident cycle, attempts, ledger and original learning clock, adds an idempotent correction/event, and returns the unresolved case to normal admission. No recipe or delivery is marked successful and no budget is reset.

`claim-path` waits within the same owner-bound command for up to twenty minutes when the only blocker is confirmed exclusive implementation ownership held elsewhere. It records no path while busy and maintains the ordinary operation heartbeat. Keep that command's handle until terminal completion; never start a second claim command. Ownership/lease loss, any failed or ambiguous operation, invalid source and sealed provenance remain stops. A bounded `deferred_busy` result means the repair is still unresolved, not permission to edit without authority or transfer another owner's claim.

The same source-bound data-only full mission may own the first zero-attempt BROWSER_ADAPTER_RETRY public read without claiming a second legacy stage batch. The verifier requires its parsed one-course action plan, unchanged provider fingerprint, current actionable public access and no claimed code. The immutable claim event count stays unchanged; appended read progress is eligible only from the same batch runtime, within the batch lifetime, without a final factual or technical disposition. Fresh research contexts bind the updated ledger digest, so an earlier context must be refreshed. Attempted/exhausted stages, source/owner drift, technical access barriers and LOCAL_READER_ONLY routing remain fenced. Scheduling that read records no monitoring or delivery success.

For this mission, settled negative verification returns `repair_required` with `ownershipRetained=true` instead of closing another retry batch. Read the fresh owned packet and failure. Keep this owner, batch and lease; diagnose a different correction, reserve additional paths, register the new descendant release, and verify it. An unchanged retry is not a different approach. This return is not a pass, durable closeout or permission to rerun an unfinished/failed protected command. Source, generation, ownership or access drift still stops the affected operation.

The normal scheduler may continue the same completed/error-null native owner once per tested runtime even when no release changed. This is bounded diagnostic follow-through, not another discovery attempt or permission to repeat a verifier. Validate fresh research context and use its explicit tooling-repair scope when available. An owned read's monitoring observation uses a diagnostic `PLAYBOOK:...` fingerprint, distinct from the incident fingerprint. Fresh full-repair research reconciles it only when the source, exact incident, timestamp, read path and fingerprint match a validated same-runtime ledger entry appended after the claim. Keep a private hypothesis/evidence/fix/test record linked to retained verification and commits. Existing append-only discovery, playbook, verification and release history provide durable product evidence. Never overwrite failures, invent completed stages or create another scheduler.

Keep model waiting separate from the verifier's internal polling cadence. Retain one command handle and wait up to fifty seconds for new output (`write_stdin` with empty input, `yield_time_ms: 50000`, and bounded output, or the equivalent wait on an existing tool cell). Do not wake the model every one or five seconds, start a duplicate command, or repeatedly reload unchanged packets while that owned command is running. Use meaningful progress updates within the host's responsiveness limit.

Only a durable current `RESTORED` or factual `FINAL_DISPOSITION` permits normal provider closeout. Customer recovery stays separate and open until actual active alerts have fresh normal checks, healthy continuation and provider-accepted matching/recovery email. An empty dispatch table is not no demand. Observe the normal outbox and read Gmail when available for inbox evidence. Never send/resend email manually, mark delivery successful or alter alert inputs for a pass.

After controlled restart, prove saved-method reuse separately with changed parameters and discovery/model calls disabled. Compare recipe ID/hash and normal matches. Late recovery cannot pass the original fifteen-minute contract.

## Distinguish a failed tool from a failed venue

A complete, attributable exception in an offline pure diagnostic fixture is local development feedback after source inspection proves there was no protected operation, credential use or uncertain side effect. Preserve the stack trace, correct the fixture/input or claim the actual product path before fixing code, and run the changed local check. Follow the assigned-worker contract's narrow local-debugging rule. Unknown crashes and failed setup, provider, production, identity, ownership, lease or access operations retain their stops. A malformed local test input never establishes a venue limitation.

A terminal ordinary public-read error may justify a different read-only approach after side effects and authority are known: rendered browser instead of failed HTTP, frames instead of root text, or official source research instead of the same guessed route. Preserve the error and changed hypothesis. This exception never permits booking actions, authentication, challenge solving, replaying ambiguous mutations, ignoring denied access/URLs, or operating after lease/source/owner drift.

An absent site, persistent outage, private inventory, necessary authentication/challenge, or officially phone-only booking requires current corroborated evidence. Model-budget exhaustion, missing metadata, browser startup failure, parser bugs, lease expiry and stale deployment are **engineering limitations**, not findings that no person can find times. Retain the open customer case and exact blocker. Incomplete extraction never means no availability. Measure actual timing; do not promise every human-readable site is automatable within fifteen minutes.
