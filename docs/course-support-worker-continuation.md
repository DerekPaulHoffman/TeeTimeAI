# Continue an existing simulator worker

The human approved bounded recovery of the same existing native worker. This is part of the sole ten-minute course dispatcher, with the existing model, new-chat limit, occupied-venue limit, provider coordination and no-email boundary. It never creates a replacement, replays the first-turn launcher, transfers ownership or resets research budgets. Outdoor continuation remains outside this first simulator recovery contract.

Use only private `value.continuationItems` from the health-bearing preflight's original successful plan. Do not run a second planning inspection or select another incident. An empty new-launch list does not make returned continuation attention healthy or complete. Keep private assignment, native, source and receipt references out of prose.

For a candidate, obtain a fresh supported `wait_threads` snapshot for its exact existing thread. Its latest turn must be completed with no error or approval, with no active turn; `notLoaded` alone proves nothing. A terminal failed command marker for that exact completed turn is evidence of the stopped command, not active execution or permission to retry it. The factory must validate its observed terminal shape; an active, mismatched or unknown marker stops this candidate. Locate the original private launcher receipt from its original parent when needed, using supported `read_thread` only for that parent and extracting the actual launcher `--receipt` path. Preserve that file. Verify its exact thread and own managed checkout, native identity, `never`, `dangerFullAccess`, `:danger-full-access`, zero approval requests, and that the original launcher/server processes ended. A missing, ambiguous or different receipt stops this candidate.

Readiness must come from actual original-receipt and private-runtime observations. Never manufacture successful booleans or infer readiness from Postgres RUNNING. Verify the same repository/project and the exact current main tooling release with independent Ready production alias readback. The original worker performs its own clean branch refresh and native identity check in the continuation; the parent never changes its files, runtime or bindings.

Build an ignored private UTF-8 JSON receipt with `buildCourseSupportContinuationRequest` in `src/lib/automation/course-support-continuation.ts`, supplying the actual compact native snapshot, original launcher receipt bytes, process inspection, private-runtime inspection, read-only browser smoke, Git ancestry exit code and Ready production proof. The supported compact snapshot omits active-turn and approval counters: the factory derives no active turn from an exact idle/notLoaded state plus a completed, error-free latest turn and no active, pending or attention evidence. The separately verified original launcher receipt supplies the never-approval profile and zero approval requests. `notLoaded`, a database row or missing fields alone are insufficient. The factory hashes the original receipt bytes and checkout identity without printing them and includes `reviewedToolingRepair` only from the exact Ready Git/main release and both aliases. Keep observations within the two-minute freshness window. Do not place claim tokens, provider data or recipients in this file.

Run one standalone production command from the exact selected parent checkout:

```powershell
npx vercel env run -e production -- npm run automation:course-dispatch -- continue --assignment-ref <assignment-ref> --receipt-file <private-json-file>
```

Continue only on acquired ownership and `reserved:true` for that exact original thread. Reservation atomically revalidates source, demand, incident, checkpoint and continuation limits. At most one continuation is admitted per tick and two per assignment/source. The same failed checkpoint cannot be requested twice. An ambiguous PENDING delivery retains ownership and is never automatically replayed.

Immediately before sending, take one fresh compact native snapshot and require the same completed turn with no newly active turn or approval. If it changed, preserve the reservation and report attention; do not send or cancel it. Read and cache the complete `docs/simulator-support-continuation-worker.md` text, substituting only the exact assignment, selected checkout, native thread, returned scope and verified tooling SHA. Send that text once through supported `send_message_to_thread` to the exact reserved existing thread, without model/thinking overrides. This explicit human-approved same-worker recovery is the only scheduled follow-up permitted here. It is not a launcher operation.

After the tool successfully returns the exact original thread, write a private `courseSupportContinuationSentRequestSchema` receipt with the returned continuation key, original child and actual supported tool acceptance. Run:

```powershell
npx vercel env run -e production -- npm run automation:course-dispatch -- continued --assignment-ref <assignment-ref> --receipt-file <private-send-receipt>
```

A timeout, error, different thread, failed command or unclear tool outcome stops without resending. SENT means the app accepted that continuation; it does not prove a running native turn, successful provider read, monitoring, email or inbox delivery. Observe the same native thread and durable owned progress separately. Genuine access, owner, source, database and unexplained new failures remain attention. Never approve an unexpected permission request or solve login, verification, captcha, queue or checkout.
